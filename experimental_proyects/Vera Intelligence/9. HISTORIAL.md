# Historial de Vera Intelligence

Este documento es el archivo cronológico completo del proyecto: auditorías campo por campo, bugs
encontrados y corregidos, resultados de banco dorado por cliente, decisiones de diseño con su
justificación, y el detalle de cada onboarding. Vive separado de `8. README.md` a propósito: el README
es la referencia densa (arquitectura, cómo correr todo, estado actual, qué falta) para que alguien —
humano o LLM — entienda el proyecto rápido; este archivo es el "por qué" y el "cómo se llegó" de cada
decisión, para cuando haga falta el detalle.

**Cómo leer esto**: está en orden cronológico aproximado dentro de cada bloque temático, no es un
changelog estrictamente lineal — el proyecto avanzó con varias líneas de trabajo en paralelo (onboarding
de clientes nuevos, iteración de Data Maps existentes, automatización). Cada sección lleva fecha. Si
buscás el estado VIGENTE de algo (qué versión de Data Map usa un cliente, qué bugs siguen abiertos), no
lo asumas de acá — confirmá contra el `config.yaml` real del cliente y contra la sección "Qué falta /
QUEDA ABIERTO" del README, que es la lista viva.

## Estado

Este workspace contiene Vera Intelligence: un asesor de negocio en lenguaje natural para gerencia y
C-level, que responde sobre resultados, tendencias, desempeño, oportunidades y criterios comerciales
sin exponer cómo se almacena o procesa la información. La carpeta está organizada **por cliente como
jerarquía máxima** (`clientes/<client_id>/`): todo lo específico de un cliente (Data Map, config,
banco de preguntas, resultados de evaluación) vive bajo su carpeta; el código (`scripts/`, `tests/`)
es compartido y client-agnostic, seleccionado en tiempo de ejecución con `--client <client_id>`.

Convención de nombres de carpeta (2026-09-07): cada carpeta bajo `clientes/` lleva un sufijo de grado
de funcionamiento puesto a mano tras evaluar/iterar el cliente — `_alto`, `_medio` o `_bajo` — para que
el estado se vea directamente en el nombre sin abrir ningún Data Map. Es un juicio curado, no un
número mecánico: refleja tasa de éxito del banco dorado, cobertura real de datos y si quedan
limitaciones conocidas sin resolver. Es un sufijo manual: sólo lo cambia una persona tras revisar el
cliente (el poller y `data_map_auto_update.py` nunca tocan el nombre de la carpeta).

## Historial de la automatización del Data Map (data_map_auto_update.py)

> Nota: la sección "Flujo", "Cómo correrlo", "Por qué el gate usa el modelo real" y "Costo real medido"
> quedaron en el README (son referencia estable). Lo que sigue acá es el historial completo de cómo se
> diseñó, probó y calibró el gate diferencial, con cada hallazgo real encontrado en el camino.

### Nota de continuidad: dos hallazgos reales de las primeras corridas end-to-end (2026-09-02)

**1. Cache frío interpretado como cambio de prompt.** La primera prueba end-to-end contra Farma24
disparó una regeneración completa e innecesaria: el rulebook `conversation_insights` nunca se había
cacheado en disco (sólo `sales_evaluation` lo estaba, `.runtime/business_rules/farma24/`), así que
`old_version is None` se interpretó como "cambió el prompt" en vez de "nunca lo vimos". Se cortó la
corrida a mano (`config.yaml` nunca llegó a tocarse, el gate no había terminado) y se corrigió
`detect_rulebook_changes` para que un cache vacío sólo
establezca la foto base sin disparar regeneración. Verificado después: con el fix, una corrida sin
cambios reales devuelve `{"status": "sin_cambios"}` en segundos, sin llamar a Gemini ni a Postgres.

**2. El gate original (contra `respuesta_esperada` congelado) tumbaba TODO, siempre.** Al forzar un
cambio real de prompt para probar el flujo completo (bajando a mano la versión cacheada de
`sales_evaluation`), la regeneración funcionó bien (Data Map V4 válido, verificado con SQL real), pero
el gate original rechazó 19 de 20 preguntas con el 100% de los números "faltantes" en cada una — patrón
demasiado uniforme para ser 19 errores reales del agente. Diagnóstico con una pregunta suelta (q01):
el agente respondía correctamente **247.556** conversaciones analizables, no las **247.196** congeladas
en el banco dorado del 31/08 — Postgres QA de Farma24 ingiere ~650-700 filas nuevas por día, así que
cualquier conteo absoluto queda desactualizado en horas. Comparar contra un número congelado en una
base que crece a diario **falla todos los días sin importar si el Data Map está bien o mal** — no es un
gate, es un bloqueo permanente, e invalidaría por completo la premisa de "sin revisión humana" (nadie
podría confiar en un gate que rechaza sistemáticamente cambios buenos). Se rediseñó `run_gate` para ser
**diferencial**: corre cada pregunta contra el Data Map vigente y el candidato en el mismo momento, y
compara esas dos respuestas entre sí en vez de contra un valor fijo — ambas ven la misma foto de
Postgres, así que cualquier diferencia refleja el cambio real del Data Map, no el crecimiento natural
de la base. Costo: se duplican las llamadas del gate (~$1.60 en vez de ~$0.80 por corrida en Farma24).
**Limitación conocida que queda abierta**: si el prompt cambia de forma que *debería* cambiar
legítimamente la respuesta a una pregunta dorada (ej. una regla nueva que afecta justo el criterio que
esa pregunta mide), el gate diferencial lo va a marcar como fallo igual, aunque sea el comportamiento
correcto — es un falso rechazo, no un falso positivo, así que es el error más seguro de los dos, pero
significa que una actualización legítima con ese perfil también queda bloqueada para revisión manual en
vez de promoverse sola.

**3. Variabilidad normal del modelo, no una regresión.** Con los dos fixes anteriores aplicados, se

### Causa raíz de `q16` de Mens Fashion, investigada y corregida (2026-09-02)

Se corrió la misma pregunta de `q16_tasa_compra_segun_pregunta_ocasion` 6 veces seguidas contra el
agente real (`--internal-debug`, capturando el SQL exacto de cada corrida) para ver qué generaba el
modelo en las corridas que fallaban. Encontró **dos causas raíz distintas, mezcladas**:

1. **Fuente dual no documentada.** `hubo_pregunta_ocasion_de_uso` (`categorical_insights`, boolean,
   la fuente correcta del banco dorado) y `vendedorpreguntaocasionuso` (`performance`, checklist, enum
   Sí/No/N/A) son dos mediciones **independientes** de si el vendedor preguntó la ocasión de uso — el
   Data Map nunca documentaba que son campos distintos. En 2 de las 6 corridas, el agente hizo un JOIN
   entre ambas vistas y usó `vendedorpreguntaocasionuso` como si fuera lo mismo, dando poblaciones
   totalmente distintas (No=10.181 vs false=13.710). Verificado contra Postgres (cruce por
   `conversation_id`): sólo coinciden en ~72,5% de los casos.
2. **Filtro `usefulforanalysis` agregado sin que correspondiera.** En otra corrida, el agente agregó
   `AND usefulforanalysis IS TRUE` a la consulta aunque la pregunta no lo pide y la propia regla del
   Data Map dice explícitamente "cuando la pregunta se refiera a conversaciones analizables" (esta no
   lo hace) — la regla positiva estaba clara, pero el caso negativo (no aplicarlo por costumbre) nunca
   se dijo en voz alta. Esto reproduce exactamente el número incorrecto que había tumbado el gate
   (11.347).

**Fix, en `VI Data Map Mens Fashion V5.yaml`** (`config.yaml` ya apunta ahí):
- `semantic_dependencies.ocasion_uso_dual_source` (nuevo): documenta que ambos campos son
  independientes, con los porcentajes de coincidencia reales verificados, y ordena usar siempre
  `hubo_pregunta_ocasion_de_uso` para preguntas de negocio sobre esto — mismo patrón que
  `resultado_dual_source` en otros clientes.
- `profiles.standard_conversation.quality_filter`: se agregó la regla negativa explícita ("si la
  pregunta NO menciona analizables... NO agregar este filtro por costumbre").
- `sql_rules.categorical_rate_general_rule` (nuevo, mismo patrón que Farma24 V4): generaliza
  `performance_rate` a cualquier campo categórico booleano o Sí/No/N-A del Data Map.
- De paso, corregido `hubo_pregunta_ocasion_de_uso.nullable` de `false` a `true` (declarado mal, tiene
  43 filas NULL reales verificadas).
- `q16` del banco dorado se marcó `es_trampa: true` con la regla documentada.

**Verificado que el fix funciona**: se repitió la misma pregunta 5 veces más contra el Data Map V5.
**5 de 5 corridas limpias** — ninguna volvió a cruzar con `performance` ni agregó el filtro de más,
todas dieron el mismo número correcto (6.635/3.076/46,36%, coincide exacto con la base real). Antes
del fix, 2 de 6 corridas fallaban de la misma manera.

### Investigación de las filas huérfanas de descriptive_insights (2026-09-02)

Verificado contra Postgres QA: el origen **no es un bug ni conversaciones borradas** — es un corte de
arranque de pipeline. El 100% de las filas huérfanas de `descriptive_insights` (y las 52 de
`performance`) tienen `uploaded_at_local` **anterior** a la fecha mínima de `demography`
(2026-06-02 06:01:13). El volumen diario de `demography` ya arranca a régimen normal el primer día
(2287 filas, similar a los días siguientes) — es un go-live limpio del pipeline de checklist el
2026-06-02, mientras que el pipeline de insights ya venía ingiriendo desde el 2026-05-13, tres semanas
antes. Toda conversación subida en esa ventana tiene lectura de insights pero nunca tuvo checklist.

**Hallazgo lateral no documentado hasta ahora**: `descriptive_insights` (`vw_farma24_insights_descriptivos_generales`)
dejó de recibir filas nuevas el **2026-08-05** (216.346 filas, `last_updatedat` máximo = esa fecha —

única de las 6 vistas con este comportamiento; las otras 5 siguen actualizándose hasta hoy
(2026-09-02). No se investigó la causa (requiere revisar el pipeline de insights descriptivos
generales, fuera del alcance de este Data Map) — sólo se documentó el impacto: el motivo textual de
no-compra y business_month/business_year de esta vista no reflejan conversaciones posteriores al 5 de
agosto.

El conteo de huérfanas subió de 48.752 (auditoría 31/08) a 52.878 (hoy), aunque `descriptive_insights`
está congelada y ese total no debería moverse por sí solo — es matemáticamente compatible con que la

creciendo: 257.551 → 258.198 filas). No se confirmó esta hipótesis (no hay snapshot histórico de

### Por qué se onboardeó como TRES clientes separados, no uno con múltiples business_rulebooks

`client_config.py`/`vi_agent.py` sólo soportan **un** `sales_evaluation` y **un** `conversation_insights`
por cliente: el `system_instruction` de `vi_agent.py` describe esas dos claves con semántica fija y
hardcodeada ("Elegí sales_evaluation para atención/desempeño del vendedor... conversation_insights para
resultados, motivos..."). Forzar los 3 checklists de Huerpel (roles y protocolos completamente distintos:
recepción de autos nuevos, recepción de seminuevos, venta consultiva de piso) bajo esas dos claves fijas
perdería especificidad real de negocio, y extender el esquema para soportar N pares de rulebooks por
cliente es un cambio de código compartido (`client_config.py`, `vi_agent.py`) que afecta a los otros 17
clientes existentes — fuera de alcance para un onboarding sin supervisión humana en tiempo real. Se
onboardeó entonces como **tres clientes independientes** (`huerpel_hostess_alto`,
`huerpel_hostess_seminuevos_medio`, `huerpel_ventas_alto`), mismo criterio que ya separa a Roberts/Mens
Fashion y Maga/Farma24 pese a compartir características. Justificación completa documentada en el
`config.yaml` de cada uno.

### Data Maps V1 (2026-09-08) — hallazgos reales encontrados en la auditoría inicial

Construidos con el mismo método que el resto del proyecto (prompts completos de Langfuse +
`information_schema.columns` + verificación empírica con `GROUP BY`/`SELECT DISTINCT`):

- **Campo muerto verificado en ambas sub-marcas de Hostess**: `demography.tipointeraccion` está **100%
  NULL** tanto en Hostess (5.609/5.609) como en Hostess Seminuevos (673/673) — el campo existe en el
  shape físico de la vista (igual que en el resto de los clientes del proyecto) pero nunca se puebla.
  Consistente con que el rol de hostess/recepción no decide ni observa el resultado final de la venta
  (eso es rol de Ventas). `demography.generocliente`, en cambio, sí está poblado normalmente en las tres
  sub-marcas. Documentado como limitación explícita en ambos Data Maps: no existe ninguna fuente de
  "resultado de la interacción" para las dos sub-marcas de Hostess.
- **Filas con `conversation_id` NULL en Ventas** (hallazgo corregido en V2, ver más abajo):
  `rendimiento_vendedor` tiene 1.942 filas pero `demografia` sólo 1.707. La hipótesis inicial (V1) fue

  verificación de q03 del banco dorado (ver más abajo) permitió afinar la causa raíz real: las 235 filas
  de diferencia tienen **`conversation_id IS NULL` directamente en la vista de performance**
  (`SELECT COUNT(*) FROM vw_huerpel_ventas_rendimiento_vendedor WHERE conversation_id IS NULL` → 235),
  no un problema de integridad referencial entre vistas. Sigue **QUEDA ABIERTO** el motivo de fondo (no
  investigado el pipeline), pero el mecanismo exacto ya está verificado y documentado en el Data Map V2.
- **`prompt_id` no identificado en Ventas**: 57 de 1.942 filas de `rendimiento_vendedor` (2,9%) tienen
  `prompt_id='O7fesqEq1wN5oQXSOEcT'`, que no coincide con ninguna versión revisada (v1, v2) del prompt
  `clientes/Huerpel/Ventas/checklist` en Langfuse. De esas 57, 41 están marcadas
  `estado_analisis='Analizada'` y `usefulforanalysis=true` pero los 18 campos del checklist son NULL
  reales (no `"N/A"`). Efecto práctico: no distorsiona las tasas de cumplimiento (los NULL se excluyen
  naturalmente de Sí/No) pero sí un `COUNT(*)` crudo sin filtrar. **QUEDA ABIERTO** — no identificado a
  qué prompt/versión corresponde.
- **Casing inconsistente entre sub-marcas**: Hostess y Hostess Seminuevos usan `Sí`/`No`/`N/A` con
  mayúscula para el checklist, pero difieren en `insights` — Hostess usa PascalCase con tilde
  (`"Fresh Up"`, `"Be Back"`) y Hostess Seminuevos usa snake_case en minúsculas (`"fresh up"`,
  `"be back"`) para exactamente el mismo concepto, por diseño distinto de cada prompt. Ventas

  PascalCase de sus propios campos de `performance`. Documentado explícitamente en los tres Data Maps
  para no asumir casing homogéneo entre sub-marcas al construir SQL.
- **Ventas es multi-tienda** (10 sucursales/BDC, 42-49 asesores), a diferencia de Hostess y Hostess
  Seminuevos que operan en una única tienda cada una — asimetría real de estructura de negocio entre las
  tres sub-marcas, no un error de datos.
- Ninguna de las tres sub-marcas tiene RAG (ningún prompt declara `geminiFileSearchStoreName` en su
  config de Langfuse, sólo `promptId`).

Se construyeron tres bancos independientes (12, 11 y 12 preguntas respectivamente, SQL verificado a mano
contra Postgres antes de correr el agente, dentro del límite de 20). Primera corrida completa contra

- **`huerpel_hostess_alto`: 12/12 limpio en la primera pasada**, sin hallazgos que corregir. Incluye

  corrección de V1, sin bump de versión formal por ser un ajuste de framing, no estructural): al reportar
  "el valor más frecuente" de un campo categórico, calcular la moda sobre la población total (incluyendo
  "no mencionado"/"no identificado" si es mayoritaria), no sólo sobre el subconjunto declarado, salvo que

## Auditoría de bugs en código compartido (2026-09-08, misma sesión — a pedido explícito "¿hay más bugs?")

Tras corregir dos bugs puntuales (client_id desactualizado en dos experimentos), se revisó el resto del
código compartido buscando activamente el mismo tipo de problema — no sólo el reportado. Se encontraron
y corrigieron dos bugs reales más, ambos con tests de regresión nuevos y verificación en vivo contra el
agente real (no sólo a nivel de función).

### Bug de seguridad real en `sql_security.py`: filtro de tenant sin calificar dentro de una CTE de una sola tabla

Documentado desde el onboarding de Huerpel Ventas como limitación conocida, nunca corregido por
precaución (archivo de seguridad crítico, sin suite de tests exhaustiva de patrones JOIN/CTE). Causa
raíz real, confirmada leyendo el código: `_has_exact_tenant_filter` buscaba el filtro de tenant en **todo
el árbol del statement**, sin restringirlo al scope (CTE/subconsulta) que realmente contiene la tabla
física — y cuando una tabla era la única de su CTE y su filtro estaba escrito sin calificar (`WHERE
seller_id = 'X'` en vez de `alias.seller_id = 'X'`, estilo muy natural cuando no hay ambigüedad posible
dentro de esa CTE), el calificador exigido (el propio nombre físico de la tabla, al no tener alias) nunca
coincidía con la columna sin calificar de la cláusula real, y la consulta se rechazaba pese a estar bien
aislada.

**Fix**: `_has_exact_tenant_filter` ahora recibe el *scope* (nodo `Select` que contiene la tabla, vía
`table.find_ancestor(exp.Select)`) y busca sólo ahí, no en todo el statement. Cuando una tabla es la
única fuente física de su scope, se acepta también un filtro sin calificar (no hay otra tabla con la que
confundirse); cuando hay más de una fuente física en el mismo scope (un JOIN dentro de la misma CTE o del
mismo SELECT), se sigue exigiendo el calificador exacto por alias, ahora buscado sólo dentro de ese
scope — más estricto que antes en un sentido (ya no puede "prestarse" aislamiento entre CTEs distintas
por una búsqueda global) y más permisivo en el sentido correcto (ya no rechaza un filtro válido sin
calificar cuando no hace falta calificarlo).

**Verificación**:
- 5 tests nuevos en `test_sql_security.py`: 2 confirman que los patrones documentados como rotos (CTE de
  una tabla + `FULL OUTER JOIN`, y `UNION ALL` de dos SELECT con filtro sin calificar) ahora pasan; 3 son
  guardrails de seguridad que confirman que sigue rechazando lo que debe rechazar (una CTE sin filtro no
  se "presta" el aislamiento de otra, un tenant incorrecto dentro de una CTE sigue bloqueado, un JOIN de
  dos tablas dentro de la misma CTE sigue exigiendo calificador exacto por alias).
- Confirmado contra el código viejo (`git show` de la versión pre-fix): el patrón sin calificar SÍ fallaba
  antes y ahora pasa; el patrón con alias explícitos en cada CTE ya pasaba antes también (la falla
  original de Huerpel Ventas fue específicamente por el caso sin calificar, no por cualquier CTE+JOIN).
- Los 19 bancos dorados completos (226 preguntas SQL) se validaron contra el validador corregido: 0
  fallos, cero regresiones.
- 43 tests del proyecto en verde tras el fix.

### Bug real en `_NATURAL_BUSINESS_WORDS` (vi_agent.py): afectaba a 7 clientes, no sólo a uno

Mismo bug de fondo que ya se había corregido para la palabra "tecnología" en Salomon (ver sección RAG del
README y el hallazgo de esa fecha) — pero por un camino de código **distinto**: `_ANSWER_LEAK_TERMS` (el
regex fijo en `response_policy.py`) ya excluía "tecnología" a secas, pero `_load_internal_identifiers`
(en `vi_agent.py`, que carga dinámicamente cada nombre de campo del Data Map sin guion bajo como
identificador a bloquear) seguía usando una whitelist `_NATURAL_BUSINESS_WORDS` de sólo 3 palabras
(`producto`, `marca`, `presentacion`) — nunca se actualizó cuando se corrigió el bug de Salomon.

Auditando los 19 Data Maps (campos `text` sin guion bajo, de longitud corta, no en la whitelist) se
encontraron **13 palabras de negocio genuinas bloqueadas en 7 clientes**:
- `atlas_alto`: `tecnologia`, `modelo`, `medida`, `firmeza`, `comprado` (todos atributos de colchón:
  memory foam/gel, nombre de modelo, tamaño, firmeza, si se compró).
- `forever_21_bajo` y `shoe_box_bajo`: `color`, `talla`.
- `steren_alto`: `categoria`.
- `tigo_alto`: `region`, `sentimiento`.
- `gac_medio` y `hyundai_bajo`: `saludo`.

Confirmado con una prueba directa (antes del fix): la frase completamente natural "El cliente valoró la
tecnología de espuma con gel del modelo Manhattan en la medida queen size" se marcaba como fuga de
"identificadores internos" para Atlas — el mismo patrón de fallo que agotaba `MAX_CLIENT_REWRITES` y caía
en `UNSAFE_ANSWER_FALLBACK` documentado originalmente para Salomon, pero sin que nadie lo hubiera
reportado todavía para estos 7 clientes (probablemente porque el banco dorado de cada uno no hizo una
pregunta que forzara al modelo a usar esa palabra exacta en prosa).

**Fix**: se amplió `_NATURAL_BUSINESS_WORDS` con las 11 palabras verificadas (`secompro`/`motivocompra`
de Steren no se incluyeron por no ser prosa natural en una sola palabra, quedan bloqueadas sin costo
real). Se dejó una nota en el código explicando que esta lista es un parche verificado a mano, no una
solución general, y que un cliente nuevo puede introducir su propia palabra corta sin que este mecanismo
la detecte automáticamente.

**Verificación**:
- 4 tests nuevos en `test_vi_agent.py` (`NaturalBusinessWordsRegressionTests`), contra los Data Maps
  reales de los 7 clientes afectados — confirman que las 13 palabras ya no aparecen en
  `_CLIENT_INTERNAL_IDENTIFIERS` y que oraciones naturales que las usan no generan ninguna violación. Un
  test guardrail adicional confirma que un nombre de campo compuesto real (concatenado, que nadie
  escribiría así en una charla) sigue bloqueado sin cambios.
- Verificado en vivo contra el agente real de `atlas_alto` (pregunta real, no simulada): "¿Qué tecnología
  de colchón es la más mencionada por los clientes y en qué modelo?" — respuesta completa, usa
  "tecnología" y "modelo" libremente en varios párrafos, sin ningún fallback ni loop de reescritura.
- 47 tests del proyecto en verde tras el fix (43 + 4 nuevos).

**Pendiente real, sin resolver**: `_NATURAL_BUSINESS_WORDS` sigue siendo una lista fija mantenida a mano,
no una solución estructural. Cualquier cliente nuevo con su propio campo `text` corto sin guion bajo

guion bajo de ≤12 caracteres) pero no se implementó en esta sesión por preferir el parche verificado y
acotado sobre una heurística nueva sin la misma validación exhaustiva.

## Segunda pasada de auditoría de código compartido (2026-09-08, a pedido explícito "seguí buscando")

Se revisó el resto del código compartido no auditado en la pasada anterior: `client_config.py`,
`business_rules.py`, `usage_tracking.py`, el resto de `vi_agent.py` (loop de tools, construcción del
chat, reintentos), y las partes centrales de `data_map_auto_update.py` (`promote`, `run_gate`,
normalización de números). No se encontraron bugs activos nuevos, pero sí un riesgo estructural real (sin
disparar todavía) y una limitación conocida que vale la pena dejar escrita.

### Riesgo cerrado preventivamente: `client_id` sin garantía de unicidad entre clientes

`ClientConfig.client_id` (el valor DENTRO de cada `config.yaml`, ej. `"atlas"` — distinto y
deliberadamente desacoplado del nombre de carpeta `"atlas_alto"`, ver el comentario ya existente en
`data_map_auto_update.py::run_gate`) se usa como namespace de cache en `business_rules.py` y
`rag_sources.py` (`.runtime/business_rules/<client_id>/`, `.runtime/rag_sources/<client_id>/`) y como
etiqueta de cliente en `usage_tracking.py`. Nada en `load_client_config()` valida que ese valor sea único
entre los 19 clientes — si alguien onboardea un cliente nuevo copiando el `config.yaml` de otro como
plantilla y se olvida de actualizar el campo `client_id:` (un error de copy-paste plausible dado que así
se construyeron varios clientes "gemelos" del proyecto), los dos clientes empezarían a compartir cache de
reglas de negocio y de RAG — en el caso de RAG, esto significaría que las preguntas de un cliente podrían
devolver contenido del store de OTRO cliente, y el costo/uso quedaría mal atribuido en
`usage_report.py`.

Verificado que HOY no hay ninguna colisión (los 19 `client_id` son únicos). No es un bug activo, es un
gap de validación. **Fix**: dos tests nuevos en `test_client_config.py`
(`AllClientsInvariantTests`), que cargan los 19 clientes de una vez y validan:
- `test_client_id_is_unique_across_all_clients`: ningún `client_id` interno se repite.
- `test_no_two_clients_share_tenant_and_an_overlapping_source`: el invariante real de seguridad detrás
  del aislamiento de `sql_security.py` — el `tenant` en sí NO tiene que ser único (las tres sub-marcas de
  Huerpel comparten `tenant='Huerpel'` a propósito, ver README > Onboarding de Huerpel), pero dos
  clientes con el mismo tenant nunca deben declarar la misma fuente física (`dashboard_v2.vw_*`), porque
  eso sí rompería el aislamiento real. Verificado explícitamente que Huerpel Hostess/Ventas no violan
  esto (fuentes disjuntas pese al tenant compartido).

Estos tests no corrigen nada porque no había nada roto todavía — están para que la próxima vez que se
onboardee un cliente con un `config.yaml` copiado de otro, un error de copy-paste en `client_id`/fuentes
se detecte corriendo la suite, en vez de descubrirse en producción semanas después.

### Limitación conocida, no corregida: `_numbers()` en `data_map_auto_update.py` puede ignorar una
tasa entera corta

`_numbers()` filtra números enteros de menos de 3 dígitos sin punto decimal (`"24"`, `"5"`, `"9"`) por
diseño explícito -evitar que el gate rechace por coincidencias incidentales como "Farma 24" o "top 5" (ver
el comentario ya existente en el código). El efecto colateral, no verificado todavía como un problema
real: una tasa de negocio genuina que resulte ser un número entero corto sin decimales (ej. "85%" en vez
de "85,3%") también quedaría filtrada y el gate no la compararía entre la versión vieja y la candidata —
en teoría, una regresión real en un número así podría pasar sin ser detectada. **No se tocó**: en todas
las respuestas reales observadas en este proyecto (decenas, a lo largo de toda la sesión), cada
porcentaje viene con al menos un decimal (son ratios exactos × 100, rara vez caen en un entero redondo),
así que no hay evidencia empírica de que esto haya causado un falso negativo real — y estrechar el filtro
sin esa evidencia arriesga reintroducir los falsos rechazos que el filtro actual existe para evitar.
Queda documentado como limitación conocida, no como bug confirmado, siguiendo el mismo criterio que el
proyecto ya aplica en otros lados (no "arreglar" algo sin medir el problema real primero).

`client_config.py` (validación de config), `usage_tracking.py` (registro JSONL), `run_evaluation.py`,

## Tool calls en paralelo (implementado) + reformulación automática de queries (probado, descartado)
(2026-09-11)

Dos ideas nuevas para seguir bajando costo/latencia sin tocar el prompt, a pedido del usuario ("probemos
el 2 y el 4, si performan bien incluilo al proyecto real").

**1. Tool calls en paralelo -incluido.** `run_tool_loop` (`vi_agent.py`) ejecutaba secuencialmente cada
tool que el modelo pide en un mismo turno (ej. `run_readonly_sql` + `search_conversations` juntas, algo
que ya pasaba antes de este cambio). Ahora, cuando el modelo pide más de una tool call en el mismo turno,
se ejecutan en paralelo con `ThreadPoolExecutor` (una sola tool sigue corriendo directo, sin el overhead
del executor). **Medido en vivo** (SQL real + búsqueda vectorial real, mens_fashion_alto, 3 corridas):
secuencial promedió 21.7s (con un outlier frío de 52.8s por overhead de conexión) vs. 4.2s en paralelo
-en runs ya calientes, ~30-40% menos. `on_tool_call` (indicador de progreso) sigue disparando para cada
tool antes de ejecutarla, en el mismo orden. Test nuevo `test_multiple_tool_calls_in_the_same_turn_run_in_parallel`
(dos tools falsas que duermen 0.2s cada una; en paralelo el tiempo total queda muy por debajo de la
suma). 140/140 tests.

**Bug real encontrado y arreglado en el camino** (no relacionado con el paralelismo en sí, pero lo
destapó al forzar dos `search_conversations` concurrentes para verificar seguridad): el lock que
serializa el acceso a la conexión reusada de Postgres en `vector_search.py` (`_connection_lock`,
agregado en la Iteración 13 para la contención de sesión) es ahora también necesario alrededor de la
EJECUCIÓN de la query, no sólo de la creación de la conexión -psycopg no garantiza que una misma
`Connection` pueda usarse desde dos threads en simultáneo sin sincronización externa. Al agregar ese
lock con `threading.Lock()` (no reentrante) alrededor de `search()`, y como `search()` llama internamente
a `_get_reusable_connection()` -que también toma el mismo lock cuando aún no hay conexión cacheada-,
quedó un **deadlock real**: la primera búsqueda de un proceso nuevo (sin conexión aún) se colgaba
indefinidamente (confirmado en vivo, >150s sin retornar). Arreglado cambiando `_connection_lock` a
`threading.RLock()` (reentrante para el mismo thread). Detectado y corregido antes de llegar a
producción, dentro de la misma sesión que lo introdujo -140/140 tests después del fix.

**Hallazgo lateral, no resuelto acá**: al diagnosticar el deadlock, una búsqueda individual de
`search_conversations` (ya con el fix aplicado) tardó entre 5s y 16s en corridas sueltas -más lento que
los ~3s documentados en la Iteración 11 de `6. busqueda_vectorial/README.md`. No se investigó a fondo si
es una regresión real (tabla creciendo, más contención de sesión) o ruido de esta sesión puntual (varios
procesos de prueba abiertos y cerrados en paralelo mientras se depuraba el deadlock de arriba) -queda
como algo a seguir, no una conclusión.

**2. Reformulación automática de queries -probado, NO incluido.** Idea: en vez de depender de que el
modelo del agente decida reformular una búsqueda débil, generar automáticamente 2 variantes más
concretas de la query (vía una llamada barata a Gemini, `thinking_level=LOW`) y mezclar los resultados.
Probado con la nuance abstracta ya conocida como débil ("resistencia de precio", ver Iteración 16 de
`6. busqueda_vectorial/README.md`): las 2 variantes generadas fueron razonablemente más concretas en
texto ("el cliente dice que está muy caro", "pide una rebaja diciendo que lo vio más barato en otro
local"), pero los resultados **no mejoraron de forma clara** -las distancias de los 3 intentos (original
+ 2 variantes) se mantuvieron en la misma banda estrecha (~0.25-0.30) que ya sabíamos que no separa
limpio relevante de irrelevante, y el contenido devuelto siguió siendo mayormente ruido (diálogo genérico
sobre tallas, agradecimientos) con apenas 1-2 fragmentos realmente sobre precio en el mejor caso. Confirma
otra vez el límite ya establecido: el problema no es la formulación de la query, es estructural al
embedding para nuances abstractas. Además tiene costo real: sin índice ANN (ver punto 2 del docstring de
`vector_search.py`), cada búsqueda ya tarda 5-16s -triplicar las búsquedas por reformulación llevaría
cada llamada a `search_conversations` a 15-50s, un costo de latencia que no se justifica sin una mejora
de precisión medible. **Descartado, no se implementó** -código del experimento queda sólo en el
scratchpad de la sesión, no en el proyecto.

## Contenido de coaching_playbook.md ampliado (más completo, mejor base provisional)

## Costo por tool, batching de get_business_rules+run_readonly_sql, y bug real de conexión SQL (2026-09-14, mismo día)

explícitamente rechazando un dashboard: "no quiero hacer un dashboard pero si estaría bueno tener el
costo de cada tool" + "el 2 hacelo si no tiene riesgo" (batchear get_business_rules+run_readonly_sql

**2. Batching de tools para preguntas de coaching**: agregada una oración a `SYSTEM_INSTRUCTION_TEMPLATE`
(sección HERRAMIENTAS INTERNAS) pidiendo explícitamente que, cuando la pregunta YA deja claro que va a
necesitar tanto `run_readonly_sql` (diagnóstico) como `get_business_rules` (recomendación) -el caso
típico de coaching-, las pida en el MISMO turno en vez de una y después la otra. Cambio de sólo texto
de prompt, sin lógica nueva -bajo riesgo real, a diferencia del experimento de `top_k` de antes (ver

**3. Bug real encontrado de paso, no buscado -conexión SQL "envenenada" tras un error**: la misma
prueba en vivo del punto 2 disparó una consulta SQL con una columna inexistente
(`vendedorofrecesolucionanteobjeccionprecio`), y las CUATRO consultas siguientes del modelo (SQL
distinto, corregido cada vez) fallaron todas con el mismo mensaje genérico
`current transaction is aborted, commands ignored until end of transaction block`, en vez de con el
error real de cada intento -el modelo terminó respondiendo sin diagnóstico numérico confirmado.
Causa raíz: `run_readonly_sql` reusa una única conexión Postgres entre llamadas (optimización de
latencia del 2026-09-11), y un error de SQL deja esa conexión en estado de transacción "abortada" del
lado del servidor -cualquier comando posterior en la MISMA conexión falla así hasta un `ROLLBACK`
explícito, aunque sea un SELECT válido. El manejo de errores existente sólo capturaba
`psycopg.OperationalError` (conexión rota) y reconectaba, pero un error de SQL normal
(`UndefinedColumn`, sintaxis, etc.) no es un `OperationalError` -nunca se limpiaba el estado abortado.

**Corregido**: nuevo `except Exception` en `run_readonly_sql` que hace `connection.rollback()` (sobre

re-lanzar el error original -`rollback()` no escribe nada, es seguro incluso con
`default_transaction_read_only=on`, sólo limpia el estado abortado para que la conexión siga sirviendo
consultas después. 3 tests nuevos (`ReadonlySqlConnectionRecoveryTests`): error de SQL hace rollback,
rollback se salta si la conexión ya está cerrada (evita tapar el error real con un error de rollback),
y `OperationalError` sigue yendo por la rama de reconexión existente sin tocar la nueva. **Verificado
en vivo contra Postgres real**: una consulta con `columna_que_no_existe` seguida de una consulta
válida en la misma conexión -antes del fix la segunda hubiera fallado con el mensaje genérico, después
del fix devolvió el resultado correcto (`{"total": 22683}`) sin problema. Este bug llevaba activo
desde el 2026-09-11 (cuando se introdujo la conexión reusada) sin que nadie lo notara -cualquier
pregunta cuyo primer intento de SQL tuviera un error rompía todas las consultas siguientes de esa
misma sesión, silenciosamente degradado a respuestas sin datos confirmados en vez de un error visible.

## Streaming de la respuesta final, con seguridad (2026-09-14, mismo día)

Última idea de la sesión de optimización. Propuesta inicial: streamear la respuesta final para
mejorar la latencia percibida. Cuestionado explícitamente por el usuario ("¿Pero que ganas con
eso?") -se le contestó con honestidad que no mueve ningún número real (mismos tokens, mismo costo,
mismo tiempo total), sólo la sensación de rapidez, y se lo descartó por no encajar con el resto de
la sesión (todo lo demás fueron ganancias medibles). El usuario pidió igual hacerlo ("hacelo me
parece bien").

Antes de programar nada, se identificó un conflicto real de diseño: la caja negra del proyecto
depende de revisar la respuesta COMPLETA (`client_answer_violations`) antes de mostrarla -streamear
en vivo significa que el usuario podría ver un fragmento con una violación (SQL, identificador
interno) antes de que la reescritura de seguridad lo corrija, porque no hay forma de "retirar" texto
ya mostrado. Se lo planteó explícitamente al usuario antes de elegir un camino; respuesta: "Streamea
igual pero ponele seguridad por favor".

**Diseño implementado** (`vi_agent.py`):

1. **`_StreamingAnswerBuffer`**: acumula texto streameado y sólo libera LÍNEAS COMPLETAS que ya
   pasaron `client_answer_violations` sobre el prefijo completo (no sólo el fragmento nuevo), y que
   nunca quedan dentro de un fence ` ``` ` sin cerrar (evita mostrar a medio formar un
   ```vera-chart/```vera-suggestions, que nunca deben verse como texto crudo). Si el prefijo hasta
   una línea tiene una violación, el buffer se marca `unsafe` y deja de liberar texto para ese
   turno -congelado, no se muestra nada más hasta que el turno completo se resuelva (rewrite).
   Riesgo residual documentado a propósito (no prometido como matemáticamente cero): una frase
   prohibida que sólo se completa DESPUÉS de una línea ya liberada podría dejar ver una parte
   inocua antes de que la parte que la completa se corte -mucho menor que liberar carácter por
   carácter (la unidad mínima es una línea completa), aceptado dado que el beneficio en sí ya es
   sólo cosmético.
2. **`_send_message_stream_with_retry`**: variante de `_send_message_with_retry` que usa
   `chat.send_message_stream()` en vez de `chat.send_message()`, con el mismo contrato de
   reintentos/tracking de uso -devuelve un objeto `SimpleNamespace` con `.text`/`.function_calls`/
   `.usage_metadata` equivalente al de una respuesta no-streameada. Hallazgo real de la API
   confirmado en vivo antes de programar (inspección directa contra Gemini real, mens_fashion_alto):
   cada chunk trae `usage_metadata` CUMULATIVO (no sólo el último), y `.text`/`.function_calls` son
   incrementales por chunk -el último chunk alcanza para reconstruir el turno completo.
3. **`run_tool_loop(..., on_text_delta=..., on_stream_invalidated=...)`**: cuando se pasa
   `on_text_delta`, TODOS los turnos (no sólo el final) van por el camino streameado -los turnos de
   tool-calling simplemente no liberan texto (no hay narrativa que mostrar antes de un
   function_call, confirmado tanto empíricamente como por la convención ya existente en los tests
   del proyecto: `FakeResponse` con function_calls siempre trae `text=""`). Si de todos modos
   apareciera un function_call después de haber liberado texto en el mismo turno (caso no
   observado, sin garantía formal de la API de que sea imposible), se invoca
   `on_stream_invalidated()` y ese texto se descarta -mismo criterio que cuando la validación final
   de todo el turno encuentra una violación y dispara la reescritura existente.

**`streamlit_app.py`**: un `st.empty()` (`streaming_preview`) vive DENTRO de `st.status(...)` -se
actualiza en vivo mientras el status está "running", y al colapsar (mismo comportamiento que ya
existía al pasar a "complete"/"error") deja de mostrarse justo cuando `_render_message` renderiza la
respuesta final persistida debajo -sin duplicado visual. `on_stream_invalidated` limpia el
placeholder si un draft se descarta.

**Verificado**: 20 tests nuevos (`StreamingAnswerBufferTests`, `StreamingRunToolLoopTests`) -líneas
